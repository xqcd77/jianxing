# 专项20题迁移到应用与界面评测

原专项独立适配器运行没有覆盖现有产品，不能用于本次三组比较。原始文件保留，旧84题跨批次拼接汇总已撤回作为本次依据。

## 统一的测量路径

冻结题目、夹具、代码与运行配置 → 每题每组独立FastAPI应用和SQLite银行账户 → 按原始用户语言调用聊天或研究API → 必要时通过真实确认/演示强验证接口办理 → 独立读取状态、账本、Grant、回执和审计 → 使用冻结前端在桌面及手机宽度回放真实响应 → 同版DOM v4 MiMo裁判 → 同题配对统计。

三组沿用64题应用评测中的S_AGENT/M_AGENT/C定义与10次模型调用上限。Single为统一领域提议及单通才研究；Multi为六领域规则提议及双研究角色；当前C为六领域规则提议及双角色有界补查。三组都共用银行权限、工具、核验、记忆与报告渲染。结果是这些具体系统配置的比较，不能泛化为所有Single/Multi架构的优劣。

## 夹具与故障控制

- 20题的账户、流水、预留、持仓、合同、产品、预计收入在真实隔离数据库建立，账本双边平衡。标准答案及必需项不进入业务上下文。
- 银行/商户原始资料使用本人范围的financial_evidence文档；实际facts和账户查询只提供索引，详情由流水详情、压力测试或产品条款工具回读，保留来源、时点与版本。此入口不授予任何操作权限。资料缺失用未知表示，不能补造零费率或到账时间。
- MA08只在首轮后注入真实外部消费，并推进到09:05；新余额源自实际账本。
- MA09故障在确认提交之前安装，真实提交成功后丢响应、暂不可查询；恢复后用原计划核实真实银行回执。原设计稿中未来成功回执占位符绝不写入数据库。
- MA10在执行屏障前，通过真实授权服务与演示验证码建立两个独立计划的有效Grant；两个线程提交不同计划，转账进入银行事务后第二请求开始，再由应用自身锁及资金预检决定结果，不直接写成功状态。
- REVOKED是当前应用停止银行代扣的实际枚举，对应题目业务语义“停扣”，不得因原稿叫STOPPED而错判。DR04使用10月16日15:30，不沿用默认10月13日。

## 解释限制

产品当前仍有日期级结算、固定规则声明库及批次政策等能力边界。专项中的精确时刻、订单关联、版本冲突和情景矩阵若未答全，按有效失败保留，不把守住未扣款当任务完成。空条款引发应用异常也是应用缺陷，不能当成功。MA04指定整批累计政策，若应用不支持，结论属于平台政策适配缺口，不能单独归因于LLM或Agent数量。
