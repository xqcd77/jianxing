# 实际使用反馈：金额、复合需求与进度追问

## 问题与修复

输入「我的4500元 给妈转1200 剩下的给我推荐一款ETF产品」时，旧的单项转账规则把第一个带单位的金额4500元当成转账金额，并把整个意图替换成了一个转账任务。现在金额直接绑定到已核实收款人的转账动作，1200元与总资金4500元分开处理；模型草案也按该绑定核对金额。

Supervisor对可明确拆分的转账与公开资料需求分别处理。该输入生成1200元的待确认转账和独立的ETF资料目标，按用户声明的资金记录3300元研究预算。两个目标随计划持久化，确认、取消、历史查询和刷新都保留各自状态。修改计划版本后，旧ETF预算标记为需要重新核查。

输入「我的6000元 给我推荐一款适合每日定投200元的ETF」时，总预算6000元与每次投入200元进入不同字段；6000÷200＝30次完整投入，不计交易费用和价格变化，不把交易次数当作自然日数。公开ETF请求使用已接入的官方基金目录，不交给演示理财目录替代。

当前公开来源只接入嘉实基金目录。目录只能核实名称、代码与官网链接；候选不代表已通过适合性判断。投资期限、风险承受能力、交易单位、价格、费率和平台定投规则仍需核查。来源失败时保留资料目标和预算，明确返回资料暂不可用，不生成产品结论或购买操作。

研究任务创建与会话指针在同一数据库事务中落盘。「好了吗」「研究完了吗」「进度怎么样」「分析结果呢」直接读取本人、同一会话的任务状态和原报告；取消、中断与失败保留真实状态。公开资料答复也能在有效期内回读。旧研究的延迟完成不会覆盖更新的会话目标。

## 刷新时的数据库争锁

页面初始化并行读取多个接口。资金预检虽然最终回滚，但临时模拟会写入SQLite；旧实现从普通读事务升级为写事务时，可能遇到运行事件已经提交的新WAL版本，导致`database is locked`和计划接口500。

预检现在使用独立的`BEGIN IMMEDIATE`事务，在首个读取前取得写入次序，并在正常退出和异常退出时始终回滚。正式办理沿用原有事务、授权与幂等规则。

## 验证范围

- API回归覆盖原始两组输入、金额与代码区分、千位分隔符、外币边界、官网不可用、计划修改、转账确认、历史回读和会话隔离。
- 并发测试交错执行预检与运行事件写入，核对模拟余额与正式账本，确保预检未提交转账。
- 浏览器验证使用独立临时演示数据库与模拟官网响应，检查两个目标、金额、刷新恢复、移动端布局和进度追问；不使用主账户进行测试交易。
- 没有据此更新历史模型评测分数。此前错误的已记账演示交易保留原始凭证；修复不对历史账本做静默改写。

本轮验证结果：最终离线回归771项通过；4项外部模型或Embedding测试未启用，1项此前已知的冻结资料哈希检查单独排除。Python静态检查和前端两套类型检查通过。浏览器验证覆盖桌面、移动端、页面刷新与公开资料进度追问，未扣款且没有前端异常。另做了一次真实官网只读查询，成功取得目录级ETF候选；这不代表个性化适合性核验已经完成。
