# 架构与方法

## 职责边界

各角色的模型调用统一经过`BankAgentHarness → Agents SDK Runner → ProposalModel`，底层保留原有服务商协议适配。SDK接收完整、经Pydantic校验的提案，不持有银行执行工具。LangGraph负责持久工作流、执行状态机与检查点；Harness负责完整请求预算与运行指标；业务网关独占实际授权与资金执行。分工由runtime_policy统一声明，详见[运行时迁移说明](runtime-migration.md)。

模型调用前由共享ContextBuilder按认证主体和会话重新读取SQL任务状态，生成只读TaskBrief，保留全部目标、参数、依赖、版本、缺项与核实后的回执引用；按目标并集选择能力和必要当前facts，再进入完整请求预算检查。交接单不另行持久化、不授予授权；角色原有证据包保持完整。详见[任务交接单与上下文装配](task-brief-context-builder.md)。

角色阶段结束后，服务端将已校验的结论、证据引用、缺项和下一步组装为RoleReturn，按用户、会话、角色与任务隔离存取，不传递私有推理。业务交接绑定规则服务补全后的节点，研究交接绑定原始来源与研究基准；每次模型调用仅对重复内容做可完整还原的结构去重，TaskBrief、当前事实及业务约束保持原值，再执行完整请求预算检查。详见[角色返回协议与阶段压缩](role-returns-stage-context.md)。

共享记忆增加写入准入与独立后台整理：原文和整理任务同事务保存，后台按用户分批精确去重、归档旧非关键会话、清理失效索引，并保护未完成任务及明确约束。简单余额查询按需读取 SQL 偏好，组合、续办和资金操作保留语义检索；关键偏好不受 Top-K 截断，所有来源继续回读校验。详见[后台记忆整理与读写策略](memory-curation-policy.md)。

入口由FastAPI处理登录、会话、业务表单、聊天与研究任务。当前默认是1个Supervisor＋4个子Agent：账单研究、理财研究、业务办理、独立核验。普通FAQ和明确单项业务走短路径，不强行唤醒全部角色。Supervisor协调目标与分流，业务办理Agent生成结构化Intent和业务DAG，六类规则服务完成参数校验；无需额外Planner。详见[Supervisor编排设计](supervisor-architecture.md)。

聊天统一经过RequestIntake；先保留源目标，再选择续接、进度、公开资料、转入或业务规划入口。每项任务保存稳定ID和版本，修改使用GoalPatch与网关参数schema，不能重放已完成步骤。capabilities从网关定义生成模型与UI共用目录，所有相关领域同时保留；外部ETF不开放本地模拟理财替代操作。详情见[架构改进与逐项验收](architecture-upgrade.md)。

研究层不是六个业务Agent的自由聊天。Supervisor与账单、理财研究角色使用分别定义的提示词、只读工具目录和输出协议；按任务通过LangGraph Send分派。账单角色核查流水、已有义务、异常和资金缺口；理财角色读取模拟披露，比较风险、起购、锁定与赎回到账，并解释排除原因。金额与筛选结论由程序核验。

## 控制图与业务DAG

银行控制图：Supervisor → 业务办理Agent → 六类规则服务 → 程序DAG校验 → 组合计划资金预检 → 按需独立语义核验 → Compile → Verify → Execute。余额不足等正常受阻先解释整单金额、缺口与下一步，不交由模型将其改判为安全异常。核验发现语义问题时，普通聊天草案可有界返回业务Agent修订；表单或研究选定的明确方案不自动改写，须由用户核对。条件变化时通过Backtrack回读当前事实，再Replan未执行步骤；默认最多3次自动修复。等待用户、预约或外部事件时中断并保存检查点，恢复后重新核验。业务计划版本递增时旧授权失效，已执行回执保留。

研究图：Supervisor → 按需并行研究 → 确定性来源检查 → 必要时定向补查 → Supervisor汇总 → 独立核验Agent → 报告。发现语义问题且仍有预算时，只补查受影响角色；到达上限仍未通过则保留已核查事实、标记待解决并关闭可办理方案。默认两轮，最多配置三轮。只有用户选择候选、重新核对当前事实后，才进入银行执行图。

外层LangGraph可以有有界反馈循环；每个计划版本的业务DAG必须无环。节点状态、余额、风险和授权决定是否能够执行，不以模型自然语言的“已完成”为准。

## 共享记忆

关键字段直接通过Pydantic传递：金额、币种、收款人、日期、否定要求、计划版本与回执引用。结构化字段不能依靠摘要重建。

L1先按用户、领域、会话、有效期过滤，再由Chroma按Embedding相关性排序；L2用TextRank提取原句，并保留金融条件；L3根据来源ID回读SQL原文，银行回执直接取正式回执表。Chroma保存向量和过滤元数据，不保存原文副本，返回ID也必须属于SQL预先筛选的候选。SQLite继续保存来源、权限、原文和可重建的向量缓存，NumPy用于向量处理与TextRank计算。FastEmbed加载中文BGE ONNX模型；lexical与lexical_fallback明确标识，不能伪装为语义检索。`BANK_MEMORY_BACKEND=numpy`仅作为显式历史对照选项。

历史余额不能替代实时余额，历史同意不能成为新授权。来源不明的文本不能成为银行事实。研究证据带来源ID、业务时间、版本和内容摘要哈希，区分用户声明与银行事实。

可更新偏好使用明确的业务key和expected_version；旧版本停止参与检索，原文继续按原权限与保留策略回读。产品快照按精确产品身份选择版本，显式来源版本不能倒退。Harness对完整服务商请求做Token预算预检，并为共享task_id的角色原子预留累计额度。请求、模型、记忆、工具读取与业务阶段使用同一运行事件结构，详见[记忆与运行控制](memory-runtime-controls.md)。

## 数据与提交

SQLAlchemy / SQLite维护账户、计划、节点、授权、回执及双边账本；AsyncSqliteSaver保存图检查点。整数分表示资金，Decimal处理比率和定点计算。适配层处理提交与未知结果核实，幂等键阻止重复扣款。

chat_tasks表维护完整请求的领取租约、进度、取消和结果。前端提交后通过NDJSON接收阶段事件，先展示可用办理部分，再补独立资料；刷新后可按任务ID恢复查看。独立Worker可以领取共享队列，过期已开始任务标记中断，不自动重放修改。SQLite写锁等待与完整任务首个可用结果耗时分别记录；公开产品资料单独保存来源、读取时间、版本与内容哈希。

研究计算只使用已读取来源：统一核对净赎回金额、手续费、工作日日历、截止时刻和多情景资金轨迹。反事实方案使用结构化参数，预计收入和研究中的投影不写入当前可用余额；结论保留来源绑定，无法核验的条件明确保留未知。

独立调度器推进预约、结算与续费；同机跨进程锁保护计划与调度领导者。当前不是跨机器分布式架构，也没有将研究任务描述成已经实现的分布式断点续跑。

核心实现入口：bank_agent/supervisor.py、supervisor_agents.py、supervisor_banking.py、supervisor_research.py。银行执行与数据基础仍在graph.py、research_tools.py、memory.py、engine.py、adapters.py与services/。`BANK_ORCHESTRATION_MODE=legacy`保留旧实现供历史对照；历史分数不能直接归因于此次新架构。完整图见仓库README。
