# Supervisor＋4子Agent：BAD CASE分析与修复

## 分析范围与基准

对2026-10-19第一轮48题评测中的8道失败、2道未决，回读实际应用响应、模型结构化输出、研究来源和审计事件。修复前：严格通过38/48（79.17%），五维等权4.23/5，2∶2∶1∶1∶1加权4.29/5；业务基础检查48/48。它们是不同指标，基础检查通过不代表任务完整完成。

题集、必需要求、MiMo v8评分规则保持不变。修复后的完整应用执行与桌面/手机界面回放另存新运行目录，不替换原记录，也不从不同版本挑选成功样本拼接成绩。该题集已参与开发，是诊断回归而非独立盲测。

## 根因与修复

| 样本 | 从运行证据确认的问题 | 实施修复 |
| --- | --- | --- |
| cards_virtual_apply | 卡片确实创建，但没有解释身份资料有效属于合成演示前提，用户易误以为Agent完成真实KYC | 开卡回执明确演示前提、真实银行审核与认证边界 |
| special_ma01 | 正确核查风险匹配与起购条件，但没有区分候选资格与本金收益保证 | 理财研究统一保留资格、风险、本金损失及未来净值的不确定性说明 |
| special_ma02 | 模型将业务问题分配到错误核验目标、虚构证据ID，程序拒绝后只显示核验不可用；没有展示已可算出的整单缺口 | 在语义核验前运行同一银行规则的整份计划模拟，明确总需求、当前可用、缺口及补款/重新选金额路径；受阻时不执行任何步骤。核验输出结构错误最多修正一次 |
| special_ma03 | 已撤销银行代扣并保留商户合同，但回执未说明本次没有整卡冻结或修改普通支付限制 | 补足订阅与卡片状态的操作边界；其他支付仍取决于卡片当前状态和银行规则 |
| special_ma07 | 已生成通道限额解释，却只写入message；有计划的界面读取assistant_message，造成用户看不到 | 同步用户实际展示字段；保持本题银行规则的适用范围，不改限额、不跳过认证 |
| special_ma08 | 同一笔“给妈妈”的拟转账被同时作为转账和声明支出扣两次，导致程序安全上限也错 | 对收款人及金额一致的同一事项去重；同金额但不同用途不合并。展示整单需求、缺口与待用户选择的缩减方案，条件变化后旧确认不沿用 |
| special_dr01 | 已区分预授权与真实入账，却缺少仍有异议时的核实入口 | 按条件说明订单、商户订单、银行回执核对及争议核查入口，不自行退款或撤销合同 |
| special_dr06 | 把“23日9点需要钱”答成当日17点到账；独立核验也未发现 | 提取并约束到具体用款时刻，按受理截点、营业日历和到账时刻倒推最晚申请边界；缺字段仍保留未知 |
| special_dr07 | 合法round(...,4)中的精度4被当作无来源财务操作数，连续拒绝后退回无关的申购表 | 区分精度语法参数与财务操作数，保留伪造金额拦截；程序绑定份额、净值、费用与锁定/到账时点，区分新申购门槛和既有持仓赎回 |
| special_dr10 | 多个互斥方案被单一预算模型摊平；核验输出无效后报告又被通用统计替代 | 提取有类型约束的独立方案，每个方案分别计算按时/延期收入与付款前后现金；核验服务失败时仅保留可复算、来源绑定的事实，不提供可交易选项 |

## 方法与安全约束

1. 资金、费用、时点和情景矩阵交给只读计算，模型负责理解、证据关联和解释。新实现不读取评测答案或样本ID，计算依赖实际查询结果与用户明确条件。
2. 对核验输出格式、目标、引用错误实行一次有界协议修正；有效的负面核验不因不通过而重试，也不将补查当作用户授权。
3. 研究降级时不再用一个无关的通用模板覆盖已核查事实；仍关闭所有办理选项，明确未通过独立核验。保留事实不代表允许执行。
4. 所有交易继续经过银行规则、余额、当前状态、版本与授权检查。补充解释不是降低分数要求或放宽资金与认证控制。

## 验证

新增回归覆盖：同一转账去重、同金额不同支出不去重、round精度与伪造操作数、节假日前倒推、锁定期与T+1、互斥方案交叉收入情景、模型金额/时点来源约束、核验协议修正及负面结论停止、整单资金受阻零写入。

原始基准：`.data/evaluation/bankflow_lite48_supervisor_20261019_v1`。

第一版修复完整执行过程中，额外暴露AA工具名称偶发输出`funds.aa.create`的问题。应用此前正确拒绝不存在的工具，但直接报错中断了任务。补充精确目录规范化：仅在移除重复领域前缀后，工具确实存在且仍归属同一领域时接受；未知工具、跨领域名称仍拒绝，进入原有有界协议恢复，不能新增能力或跳过授权。

第一版修复记录完整保留于`.data/evaluation/bankflow_lite48_supervisor_repairs_20261019_v2`；补充该修复后，另起`.data/evaluation/bankflow_lite48_supervisor_repairs_20261019_v3`完整运行48题，不复用前一版的成功任务。

后续回放还发现：模型有时提前将资金不足作为`reject_reason`返回，根本未进入计划预检，因此仅修复预检分支不够。新版业务提示要求将已知业务及参数交由银行规则核验；对“正常条件不足”的提前拒绝只允许一次结构恢复，仍保留原始范围与参数，安全拒绝不能进入该恢复分支。已用真实接口验证5500元需求、5000元可用、500元缺口及零部分执行的解释。

同样补充条款索引关联：持仓摘要以`terms_id`关联完整合同而不直接带产品ID时，仍沿显式来源关系计算；分别处理受理后T+n、不同截点、日限额、营业日历与用款时点。不能用模型所知“今天”覆盖银行的合成业务时钟。新增了不同金额和不同截点的测试。

资料注入防护保留异常操作指令的隔离说明；模型叙述未通过核验时，保留可复算事实和规则核验过的无关比较，关闭交易选项，不将整份研究变成空白拒绝。

最终完整回归独立保存于`.data/evaluation/bankflow_lite48_supervisor_repairs_20261019_v4`，不把v2/v3的成功题拼接进来。

已完成一次全量测试：703项中699通过、4项按既定条件跳过。最后修订再通过73项针对性回归；前端两套TypeScript类型检查通过，新增Supervisor模块静态检查通过。

判分过程中MiMo曾返回HTTP 402；服务恢复后已使用v4冻结输出接续完成判分，没有改用人工自评或重新办理来挑选更好结果。最终2道裁判格式错误按同一输入与标准有界补判成功，原始记录保留，其他有效负面判分没有重抽。

## 最终结果

同一架构、相同48题、MiMo v8标准、每题1轮，修复前后对照：

| 指标 | 修复前v1 | 修复后v4 |
| --- | ---: | ---: |
| 严格任务通过 | 38/48（79.17%） | 44/48（91.67%） |
| 需求覆盖 | 4.3125 | 4.7292 |
| 银行业务正确性 | 4.5435 | 4.7826 |
| 证据与推理 | 4.0000 | 4.7083 |
| 可操作性 | 3.9375 | 4.2708 |
| 清晰度 | 4.3750 | 4.5208 |
| 五维等权宏平均 | 4.2337 | 4.6023 |
| 五维加权评分 | 4.2892 | 4.6462 |
| 业务基础检查 | 48/48 | 48/48 |

严格通过净增6题、提高12.50个百分点；加权评分提高0.357分。原10道失败/未决中9道本轮通过，1道仍未完整通过，同时3道原通过样本在本轮出现遗漏，全部纳入分母。单轮结果存在模型与裁判随机性，不能只报修复样本而隐去退步。

最终累计模型调用135次，修复前133次；每题上限均16，最终单题实际最多11次。本次未以扩大调用上限换成绩。冻结源码对比显示评测代码未变，变化集中在8个银行应用文件。
