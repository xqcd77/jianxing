# 多任务办理、前置条件导航与研究展示修复

本次针对两笔转账、剩余资金按比例理财、后续选品，以及办理与研究混合请求。所有财务回归使用隔离演示账户，不对当前页面中的个人账户执行测试交易。

## 问题与修复

1. 原来缺少产品等字段会生成顶层澄清，使整份请求提前结束；独立核验也会把某一步的业务条件不足视为整单无法编译。现在先按目标区分可办理步骤与待补步骤，保留已知金额、对象、依赖及稳定目标ID。测评不匹配等局部业务条件由对应节点暂停，整单资金不足和安全条件仍保持原有校验。
2. 待补任务保留结构化`pending_task`。选择产品、补齐已验证联系人、修改待选理财预算会接回原计划，不从历史对话重新生成转账；已经完成的节点和回执保持不变。相对预算以实时可用余额与未完成转账核对，用户明确改成固定预算后不再套用旧比例。
3. 补充常见的转账清单、中文金额、百分比及分数表达；金额和收款人仍回到银行事实及严格参数定义校验。银行内理财请求不会自动增加ETF交易提示，也不会替用户选定申购产品。
4. 风险不匹配和测评失效均提供测评入口；主动回复时打开问卷。五题需本人回答，并确认更新测评；确认后自动返回原计划重新核验。大额转账定位到待验证卡片，分析任务定位到研究报告，不自动代替用户提交资金授权。
5. 页面先展示办理进度，再展示研究。研究按“结论与关键数字、分析框架与依据、产品条件对比、下一步”排列，详细证据及已完成步骤结果默认折叠，保留展开及原文查看入口。

## 原始案例的预期行为

以可用4500元为例：

```text
妈妈400元：独立确认
另一位已验证联系人1500元：按日累计规则验证
理财预算：(4500 - 400 - 1500) × 20% = 520元
产品比较：只读，不自动申购
理财申购：保留520元及转账依赖，等待选择产品
```

若“老王”不在已验证联系人中，仅其1500元转账等待确认收款人，不会猜成“小王”，也不会丢弃妈妈的转账。补齐联系人后可继续原目标。选择风险R3的模拟30天产品而当前测评为R2时，进入本人测评或改选流程；更新测评仍不等于申购授权。

## 验收

- `tests/test_multigoal_followthrough.py`覆盖19项检查，包括原句、标点变化、中文金额、转账清单、未登记联系人、预算调整、选品续接、无重复转账、混合研究和异常金额。
- `scripts/evaluate_multigoal_followthrough.py`使用当前配置的真实模型，在隔离账户验证4个场景；模型耗时包含测试中的多轮交互，不能解释为单次请求的平均延迟。结果见`multigoal-live-evaluation.json`。
- `scripts/multigoal_ui_smoke.cjs`验证小额确认、大额验证、自动测评入口、测评确认后返回原计划、回执保持、结构化研究及1440/390两种宽度。
- 全量回归、静态检查和浏览器结果统一记录在`multigoal-verification.json`。修改前已经失败的冻结评测包哈希检查仍单列排除，不改写冻结数据。

最终按测试ID汇总，854项选中测试均有通过记录：完整分组回归发现1项预算目标定位回归，修复后受影响的58项全部重跑通过。另排除4项需显式启用的模型测试和上述1项已有冻结哈希问题。4个真实模型场景、桌面和手机浏览器流程均通过；浏览器还验证了测评提交后刷新，再确认测评仍能返回原计划。

真实模型场景首次核验均触发了一次输出协议修正，修正后通过；这项额外耗时已保留在模型运行明细中，不能把场景通过解释为模型首次输出均合格。

自然语言不存在任意表达都成功的保证；目标指代或联系人不明确时保留任务并澄清。未接入的证券交易、自动ETF定投及商户会员开通仍明确显示能力边界。
