# 第三批：后台记忆整理与读写策略

实施日期：2026-10-27。复用 SQL 原文、Chroma 索引、版本冲突规则与第一批 TaskBrief；不增加付费模型调用，不把历史记忆变成银行事实或授权。

## 全链路

```text
用户表达 / 正式回执 / 研究报告
  → 写入准入：业务信息、来源、权限、凭证、有效期检查
  → 同一 SQL 事务保存原文与后台整理任务
  → 后台按用户、分批领取，检查版本和当前任务
  → 精确去重 / 非关键旧记录归档 / 过期退出 / 异常来源隔离
  → 保留来源引用与派生摘要，清理失效向量、按需预热有效索引
  → 本轮请求先读取 SQL TaskBrief 和当前银行事实
  → 简单余额查询按需读取 SQL 偏好；续办、组合或资金操作保留语义检索
  → Embedding 检索 → 本轮 TextRank 提取 → 必要原文回读 → 完整请求预算 → 模型提案
  → 银行网关独立核对、授权和执行
```

## 写什么，不写什么

- 业务请求、待补信息与正式来源继续保存；金额、对象、日期、否定条件和结构化任务进度分别由原文与正式任务状态承载。
- “好的、继续、好了吗、停止、取消”等短句不再自动进入共享业务记忆，仍保留在会话历史，并由任务状态处理续办或取消。短句触发了真实业务结果时，正式回执照常保存。
- 咨询闲聊与无业务目标内容不自动晋升为业务记忆。不会把一次任务中的金额、产品选择或模型建议推断为用户长期偏好；明确偏好仍通过已有偏好接口写入。
- 凭证检查同时覆盖文字、JSON 文字和嵌套结构中的密码、OTP、API Key、访问令牌。整理发现旧记录包含凭证时隔离该条目；正常回读也不能输出凭证。
- 同键偏好仍按用户、会话、角色、key 与 expected_version 更新；后台整理不改变版本头、不用相似度覆盖原文。

未显式指定有效期时采用以下来源策略；调用者可在有效范围内明确指定：

| 来源 | 默认有效期 |
| --- | --- |
| 用户业务表达 | 30 天 |
| 明确用户偏好 | 365 天 |
| 产品快照 | 7 天 |
| 银行回执的记忆引用 | 90 天 |
| 研究报告的记忆引用 | 1 天 |

记忆引用过期不改变正式账本、回执、计划或研究报告。原文保留与回读继续受原权限、有效期及用户主动删除行为约束。

## 后台如何整理

整理任务是 SQL 中的 `memory_maintenance` 单据，仅含归属、代次、游标、状态、租约和计数，不含 Prompt 或私有推理。一次用户写入会递增该用户的任务代次，多个写入合并为一个后台任务。整理过程中又有新写入时，完成后重新扫描该代次，避免遗漏游标之前的新记录。

跨进程文件锁保证同一数据目录只有一个整理执行者；每批默认最多 4 个用户、每用户 64 条记录，过期租约可恢复。索引删除失败时，待删除 ID 和重试状态持久化，并采用退避重试；SQL 会先阻止失效记录进入检索，不能因 Chroma 删除失败继续使用旧资料。关闭服务时等待当前批次结束，再关闭索引和数据库。

| 处理 | 规则 |
| --- | --- |
| 精确去重 | 用户、会话、权限、来源类型、原文、结构化内容与冲突键一致才归为重复；不同金额、否定、收款人、来源身份或角色不做语义合并 |
| 旧记录归档 | 只归档超过活跃窗口的旧、非关键、无结构化约束的会话文本；提交前再次核对当前任务，办理中新开的会话也受到保护 |
| 关键记录保护 | 明确偏好、金额 / 日期 / 否定条件、结构化参数与未完任务不因窗口上限被归档 |
| 过期与旧版本 | 退出正常检索、清理派生向量；不复活已被替代的偏好，不复用旧版本号 |
| 来源隔离 | 凭证或正式来源不可用时标记隔离；不把损坏的缓存当原始证据继续使用 |
| 原文保留 | 移除原先写入路径中“超过 512 条便删除旧行”的逻辑；归档和重复标记不删除原文，主动忘记仍通过现有删除接口处理 |

归档、重复、过期与隔离使用服务端维护的记忆状态。原文和业务结构不被摘要覆盖；归档或重复记录在原有效期与权限内仍可按 ID 回读，正常检索只选有效条目。删除去重后的代表条目不会自动让旧重复项回流。

后台可以缓存 TextRank 原句摘录和关键原句，并保留原文哈希；它们明确标为派生上下文。正式检索仍按本轮问题提取和回读，不用无查询摘要代替完整证据。回执和研究内容在预热、整理和检索时回读正式来源，不能信任镜像文字。

## 按需读取与强制读取

- TaskBrief、当前账户、目标和网关条件继续从 SQL 正式状态读取，不依赖语义相似度。
- 无指代、无组合目标且未绑定当前办理计划的明确余额查询，使用 `current_facts_and_preferences`：当前余额由银行服务查，适用偏好从授权 SQL 原文读取，无须 Chroma 或 Embedding。
- 续办、上次 / 刚才 / 剩余等指代、组合请求和资金办理保留 `semantic_recall`，不能因为想节省耗时而忽略历史依赖。带当前计划的查询也保持保守读取。
- 用户、会话、角色、有效期及活跃状态先在 SQL 过滤，再应用候选数量限制与向量排序，避免无权或已归档记录占满候选窗口。
- 金额和否定类偏好不受 Top-K 相关性限制；命中后仍重新核对实时 SQL 权限与版本。用户撤销权限后，这些条目不能继续进入 items 或 protected 条件。
- 超过软上下文容量的关键内容进入原文回读路径，完整请求仍受 Harness 预算限制；不能截断约束来凑预算。历史余额与同意始终不能替代本轮事实和授权。

## 配置、状态与本地测量

```dotenv
BANK_MEMORY_MAINTENANCE_ENABLED=true
BANK_MEMORY_MAINTENANCE_INTERVAL=60
BANK_MEMORY_MAINTENANCE_BATCH=64
BANK_MEMORY_ACTIVE_DIALOGUES=128
```

活跃窗口是旧非关键对话的软窗口，不是所有记录的硬上限。后台循环跟随 Web 生命周期运行，与金融调度器分开；不需要用户请求等待整理完成。

- `GET /api/memory/maintenance`：登录后只返回本人任务状态、代次、最近批次统计和各状态数量。
- `memory.curated / memory.curation_failed / memory.capture_skipped`：记录计数、规则标签与错误代码，不复制原文、参数或凭证。
- `python -m bank_agent.maintenance organize-memory`：手动执行一批已知用户的整理；返回 more 时还有待处理批次，也可继续等待后台处理。
- `python -m scripts.measure_memory_policy`：临时合成数据库上的可复现测量，不接触主账户，不调用付费模型。

本次测量样例中，普通语义读取调用本地 Embedding 2 次，同一余额请求的按需读取为 0 次，关键偏好仍保留；4 条原文整理后仍是 4 条，其中 2 条完全重复项退出正常检索。模型服务商调用为 0。结果写入 `.data/memory_batch3_measurements.json`；这是单样例的调用计数，不代表全量请求耗时或模型 Token 的平均收益。

实现入口：`memory_policy.py`、`memory_curator.py`、`memory.py`，接入点为 `app.py` 生命周期与维护接口；未修改资金执行规则、评测 gold、裁判规则或历史评分。
