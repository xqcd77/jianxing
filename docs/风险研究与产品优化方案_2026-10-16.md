# 简行：风险研究与产品优化方案

研究日期：2026-10-16。本文为设计建议；除“当前实现”外，均不表示功能已经落地。此次不改动业务逻辑，也不自动更新已发布的介绍页。

## 研究依据及适用范围

1. [金融监管总局《银行保险机构操作风险管理办法》](https://www.nfra.gov.cn/cn/view/pages/rulesDetail.html?docId=1144382)：2024年7月1日起施行，将内部流程、人员、信息科技和外部事件造成的损失纳入操作风险，包含法律风险；提出风险自评估、关键风险指标、情景分析等工具。对本项目的启发是同时处理误操作、未授权、系统故障和恢复，不能只提示金额大小。
2. [巴塞尔委员会《有效银行监管核心原则》2024版](https://www.bis.org/committees/bcbs/basel-framework/standard/bcp/40/inforce/2024-04-25/published/2024-04-25)：银行风险管理覆盖识别、计量、评估、监测、报告和控制等环节。信用、市场、流动性等风险有各自管理要求。本项目不涉及真实授信或银行资产负债管理，不应将个人现金流提示包装成银行资本或流动性监管指标。
3. [BIS《操作风险稳健管理原则》说明](https://www.bis.org/publications/fsi-summary-principles-sound-management-operational-risk-psmor-executive-summary)：风险及控制自评估、事件数据、指标、情景分析可共同用于评估；控制效果需要持续监测。适合迁移为“风险事件—控制—验证—剩余问题”的项目台账。
4. [金融监管总局《金融机构产品适当性管理办法》](https://www.nfra.gov.cn/cn/view/pages/governmentDetail.html?docId=1217183&generaltype=0&itemId=861)及[官方发布说明](https://www.nfra.gov.cn/cn/view/pages/governmentDetail.html?docId=1217123&itemId=861)：2026年2月1日起施行，强调产品属性与风险、客户金融需求与风险承受能力的匹配。借鉴其披露和匹配思路，不能声称当前五题模拟问卷构成真实机构适当性合规。
5. [NIST AI RMF 1.0](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.100-1.pdf)：通过治理、情境识别、测量和管理持续处理AI风险。可迁移到模型规划、工具授权、证据和运行监测。
6. [W3C金融交易错误预防](https://www.w3.org/WAI/WCAG22/Understanding/error-prevention-legal-financial-data.html)、[警示弹窗模式](https://www.w3.org/WAI/ARIA/apg/patterns/alertdialog/)、[非打断式提醒](https://www.w3.org/WAI/ARIA/apg/patterns/alert/)与[交互动效](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions)：为重要交易提供核对、修改或可行的撤销机制；区分提醒与必须回应的弹窗；支持关闭非必要动效。

监管网站部分正文访问受限，相关条款及施行时间同时通过官网检索摘要、官方发布说明核对。以下产品和技术方案是结合资料与项目代码提出的设计推论，不是上述机构对本项目的认证。

## 必须区分的四种含义

- **授权等级**：查询、明确确认、强验证。说明如何办理。
- **业务风险原因**：对象首次使用、资金压力、锁定期、合同后果、证据不足等。说明需要关注什么。
- **产品投资风险**：本金损失可能性、市场波动、信用和流动性等产品属性。不能用一次身份验证消除。
- **业务当前状态**：可办理、等待核对、条件不满足、结果未知、安全暂停。说明现在能否继续。

合法的大额转账不应被直接称为欺诈或危险；小额交易也不应因金额低而免于身份归属、对象与授权校验。

## 方案一：统一风险评估结果，复用权限网关

建议建立确定性 RiskPolicyService，供规划预检、确认及执行入口共用。模型可以识别线索、解释条款和生成候选，不能签发授权、改变等级或解除硬限制。

建议输出 RiskDecision：

| 字段 | 含义 |
| --- | --- |
| authorization_tier | GREEN / YELLOW / RED，沿用现有策略 |
| status | 允许、待确认、待验证、条件受阻、暂停核实、拒绝等策略结论 |
| reasons | 稳定原因码、面向用户的解释、对应事实与来源 |
| consequences | 金额、余额、预留、合同或卡片状态等实际后果 |
| controls | 本次必需的核对、验证及服务端限制 |
| permitted_next_actions | 当前允许的补款、调整、核实、验证或协助动作 |
| evaluated_at / expires_at | 核验时间、有效边界；过期重新计算 |
| plan_version / fingerprint / facts_digest | 绑定计划、业务参数及所依据的事实 |

这些字段应嵌入现有计划响应，并由服务端核验，不把前端显示的结果当作执行凭证。执行事务内仍重新核对当前事实。对外文案不展示工具名、内部原因码、整数分或模型原始推理。

控制流程：意图与约束 → DAG → 计划预检与风险解释 → 核对/强验证 → 执行时再核验 → 提交或核实 → 回执与审计。无需新增拥有交易写权限的“风控LLM Agent”。

### 评估方法

先建立风险及控制自评估表：业务事件、触发条件、可能损失、已有控制、验证结果和剩余问题。影响程度可分档；发生可能性没有足够历史数据时标记“待估计”。不显示未经校准的“被骗概率”“安全分98分”。

硬规则优先，不能用风险加权平均抵消未授权、对象不明、越权访问或重复提交等问题。首次对象、异常频率等行为规则只能在有相应数据、合理窗口与误报验证后启用；演示可使用明确标注的合成样例。

## 方案二：朱砂印式敏感操作弹窗

延续纸白、墨绿、朱砂色。用户点击敏感步骤后，弹窗承接已有详情核对与强验证，避免先后堆叠多个相同的确认框。

建议视觉：细线圆圈绘出后出现感叹号，约400—600毫秒，仅一次轻微呼吸，然后静止。正文保留足够对比度；风险信息同时有文字与图标。系统启用减少动态效果时直接显示静态图标。无需动效库，SVG与CSS即可完成。

以“向妈妈转10000元”为例，假设本次之前当日没有其他支出、当前余额20000元且无预留：

> ！请核对本次大额转账
>
> 收款人：妈妈 · 已核对的账户尾号
>
> 本次金额：10000.00元
>
> 转出后余额：10000.00元；预留：0.00元；可用：10000.00元
>
> 本次转账将使当日累计超过演示分级阈值，需要验证身份。款项一旦实际转出，取消剩余计划不会撤回该笔款项。
>
> 【返回修改】 【验证并转账】

以上数值与尾号必须从服务端事实产生。只有真实存在首次收款、账户异常等证据时才显示对应提示，不凭金额虚构异常。

弹窗可键盘操作，焦点留在弹窗内；初始焦点可置于标题或“返回修改”，不能因回车意外付款。关闭后回到触发位置。异步刷新、重复点击、会话切换和计划变更时应使旧提交失效；核验超时显示重新核对入口。

## 方案三：不同风险使用不同交互强度

| 情况 | 呈现方式 | 主要动作 |
| --- | --- | --- |
| 查询余额、账单 | 轻量状态行，查询完成才显示完成状态 | 查看结果 |
| 小额转账、停银行代扣 | 温金色核对卡；支持合适的黄色步骤合并 | 确认具体事项 / 修改 |
| 大额转账、申购、挂失等 | 朱砂图标＋清晰后果＋强验证 | 验证并办理 / 返回 |
| 余额不足、锁定期未结束 | 持续显示的条件提示，不做账户危险告警 | 补足差额 / 调整 / 查看日期 |
| 有可信安全异常或验证失败达阈值 | 持续警示＋限定暂停范围＋恢复入口 | 核实身份 / 安全中心 / 协助 |
| 提交后超时，受理结果未知 | 温金色“结果核实中”，保持原请求编号 | 核实原交易，不给重复付款按钮 |

挂失属于保护动作：按赛题保留强验证，但不额外堆叠冷静期或多层阻拦。对明确安全风险需要阻断时，弹窗不能仍提供普通“继续执行”绕过入口。

## 方案四：计划资金压力与未来时间线

复用preflight中的账户、预留、已知代扣、待到账和未来事件信息。计划卡提供“当前可用 → 本次占用 → 剩余可用”的简洁分布条，展开后显示未来收支日期及最低现金余额。

例如在演示日期下，当前可用10000元，拟申购9000元，已登记七天后房租3000元：当前申购可能满足余额校验，但在未计新增收入的情景下届时有2000元缺口。提示“按已登记支出测算，房租到期可能缺2000元”，并提供调整申购或预算的选择。不能未获授权自动改变金额或预留资金。

预计工资与已到账余额分开展示；未来收入可以参与明确标注的预测情景，但不能作为当前付款可用资金。现有预留对应的同一笔义务应按来源关联，避免重复扣减。页面显示覆盖期间、数据截至时间及遗漏账外支出的可能性。

继续扩展现有压力测试：工资延迟、支出增加、赎回按条款延迟。展示假设、缺口日期、金额与可行调整，不生成未经验证的亏损概率。

## 方案五：风险随DAG和计划变更传播

在既有版本、指纹与实时复算上补充可见解释：

- 上游可用余额、合同状态、产品条款、对象或报价变化时，标出受影响的未执行节点并重新核对。
- 变更卡显示“金额500→5000”“收款人妈妈→其他对象”“日期今天→预约日”，明显说明旧确认已失效。
- 多节点合计或当日累计变化可能提高授权要求；不能用拆单或多个黄色步骤合并绕过红色验证。
- 独立节点可以有各自的继续策略；有资金或结果依赖的后续节点必须等待。UNKNOWN尚未解决时不允许替换请求重复付款。
- 已完成交易保留回执；补偿必须是受业务能力约束的新操作，不能把工作流回退说成真实转账回滚。

## 方案六：研究结论中的风险证据卡

产品比较卡并列展示风险等级、起购、锁定、赎回到账、测评匹配情况与排除理由。例：“本金可能损失”“30天内不能赎回”“赎回后并非即时可用”，优先展示与用户用款日期相关的条件。

界面分别标“产品风险R2”和“申购需验证”，避免把验证成功暗示成产品安全。原始条款来源、版本、核验时间可展开；条款缺失或证据冲突时清晰标记。缺少关键披露的产品不进入可执行候选。

“已核实事实”“用户声明”“情景假设”“待核实”采用不同标签。账单重复扣费规则只能给出异常线索，不能直接断言诈骗。否定要求如“先查询，别取消”应在研究报告与执行计划之间继续保持。

## 方案七：安全中心增加可恢复的事件时间线

保留现有安全中心，在里面增加待核对事项和脱敏事件：授权失效、验证成功、敏感步骤暂停、原交易结果核实。明确用户下一步；解除安全锁定后回到原计划重新核对，而非自动扣款。

前端文案应限定范围，例如“当前敏感操作已暂停”，避免实际只暂停交易却写成全部服务不可用。“未发现已知异常”需标注检测范围与更新时间，不能承诺绝对安全。日志不显示OTP、密钥或账户完整敏感数据。

## 落地顺序

| 阶段 | 工作 | 完成标准 |
| --- | --- | --- |
| P0 | RiskDecision统一解释；敏感弹窗；普通受阻与UNKNOWN视图；修改差异卡 | 前后端同源、可恢复、不能绕过原授权机制；无重复确认堆叠 |
| P1 | 计划压力分布与时间线；研究风险证据卡；安全中心事件 | 资金数字可追溯，假设与事实分开，风险有下一步 |
| P2 | 有数据支持的行为异常规则、跨会话聚合、风控运营指标 | 有真实口径、误报分析、规则版本和回放记录；合成演示明确标识 |

建议第一批优先：大额转账、理财申购、订阅停扣三条完整链路，再覆盖挂失和跨场景计划。

## 风险评测与验收

优先升级现有BankFlowBench中重复或薄弱的题目，不依靠加大量简单拒绝题提升通过率。每条安全样例配一条正常业务对照；例如未经授权的新收款人交易对照已验证联系人合法大额转账。

必需样例：当日999元再转2元；拆单导致累计升档；确认后修改对象/金额；跨会话同账户累计；首次对象但无欺诈证据；预算不足；待到账赎回；工资延迟；产品锁定越过用款日；停扣不等于解约；查询时明确别取消；超时已受理；重复点击；临界到期或已消费验证码；低动态偏好；键盘操作；关闭弹窗后原计划恢复。

核心指标：

- 未授权或越权写入数、重复扣款数、未知结果盲目重提数：目标为零，用真实状态和账本验证。
- 风险策略符合率：预期的自动、确认、验证、阻断是否匹配，不能把一律拒绝计为安全通过。
- 非必要打断率与正常办理成功率：衡量误报与过度确认，分别披露。
- 风险解释完整率：原因、影响、下一步和来源是否齐全。
- 恢复完成率：补款、重验、核实或协助后能否完成同一需求。
- 用户理解度：小样本任务中能否回答“转给谁、多少钱、之后剩多少、能否撤销”；动效本身不能作为安全有效性的证据。

LLM裁判适合评估解释质量；权限、真实执行状态、资金守恒和重复写入由确定性断言检查。失败和未决分别报告，风险得分与业务成功不能混成一个总分。
