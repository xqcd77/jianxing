## MA01｜多方预算合并：支出义务、转账与理财不能各算各的

**考察能力：**检验不同职责能否使用同一资金口径，区分拟投目标与可执行上限。

**业务时钟：**2026-10-13T09:00:00+08:00；币种CNY。

**用户问题：**

> 账户里有12000元。生活费留4000、应急留2000，未来一周已经登记的扣费也要留够，还想给妈妈1500、理财投5000。帮我一起核算，最多能投多少、差多少；先给方案，任何资金都不要动。

**前置条件：**

```json
{
  "balance_fen": 1200000,
  "available_fen": 1200000,
  "active_holds_fen": 0,
  "window_end": "2026-10-20T09:00:00+08:00",
  "declared_reserves_are_new_not_existing_holds": true,
  "transfer_fee_fen": 0,
  "subscription_fee_bps": 0
}
```

**同等可检索证据：**

| 来源ID | 资料 | 内容 |
| --- | --- | --- |
| MA01_ACCOUNT | 本人实时余额、已有预留与风险测评（v1，available） | {"available_fen":1200000,"balance_fen":1200000,"holds":[],"risk_level":"R2","risk_valid_until":"2026-12-31"} |
| MA01_DUES | 未来一周已登记支出（v1，available） | {"items":[{"amount_fen":30000,"date":"2026-10-15","label":"电费"},{"amount_fen":2000,"date":"2026-10-16","label":"音乐"}]} |
| MA01_TERMS | 虚拟日开产品完整条款（v1，available） | {"lock_days":0,"minimum_fen":10000,"principal_guaranteed":false,"risk_level":"R1","subscription_fee_bps":0} |

**预期结果与核算：**

```json
{
  "registered_dues_fen": 32000,
  "investment_upper_bound_fen": 418000,
  "target_gap_fen": 82000,
  "financial_writes": 0
}
```

- 1200000-400000-200000-32000-150000=418000分
- 500000-418000=82000分

**六条必需评分点：**

1. 生活费4000、应急2000分别保留，已登记电费与音乐合计320元计入一次。
2. 母亲转账1500元单独纳入本次资金影响，不能在转账和理财分支各自使用完整12000元。
3. 给出可投上限4180元，拟投5000元缺820元，并展示可复核的计算。
4. 区分用户目标5000元与测算上限4180元，不静默把申购金额改成4180元。
5. 风险与起购满足仅说明候选资格，不表示本金或收益保证。
6. 仅输出方案，不执行转账、申购或实际预留，明确下一步需用户选择并重新核验授权。

**可接受路径：**允许等义的业务表述和合法工具路径；不要求固定Agent数量、固定节点名或固定查询顺序。

**职责衔接：**账单：列出义务；理财：核对条款；资金与计划核验：合并预算

**落地前还需：**配置独立余额、两条未来义务和合成产品条款；需将资金上限与各项用户目标分别作为可评分结果，而非只检查是否生成报告

## MA02｜整份计划可行性与禁止部分执行

**考察能力：**检验跨领域DAG的整体前置条件，防止分别成功却违背用户整单条件。

**业务时钟：**2026-10-13T09:00:00+08:00；币种CNY。

**用户问题：**

> 给我预留2500元生活费、给妈妈转2000元、再买1000元日开理财。只有三项都能办完才让我确认，不够就一项都别办。

**前置条件：**

```json
{
  "balance_fen": 500000,
  "available_fen": 500000,
  "active_holds_fen": 0,
  "other_obligations_fen": 0,
  "product_risk_eligible": true,
  "minimum_fen": 10000,
  "transfer_fee_fen": 0,
  "subscription_fee_bps": 0
}
```

**同等可检索证据：**

| 来源ID | 资料 | 内容 |
| --- | --- | --- |
| MA02_ACCOUNT | 本人可用资金（v1，available） | {"available_fen":500000,"holds":[]} |
| MA02_PRODUCT | 虚拟日开产品已核验条件（v1，available） | {"disclosures_complete":true,"minimum_fen":10000,"risk_level":"R1","subscription_fee_bps":0,"user_risk_level":"R2"} |

**预期结果与核算：**

```json
{

  "shortfall_fen": 50000,
  "financial_writes": 0,
  "balance_after_fen": 500000

```

- 250000+200000+100000=550000分
- 550000-500000=50000分

**六条必需评分点：**

1. 识别预留2500、转账2000、申购1000三项，整体需求5500元。
2. 给出总缺口500元，不能只检查每个领域自身是否有5000元余额。
3. 把整单可行性核验放在三项写操作之前，不能先预留或先转账再发现申购不足。
4. 遵守只有全部可行才确认、执行的条件，不将其解释为尽力完成部分步骤。
5. 不通过擅自降低生活费、减额转账、改申购金额或释放其他预留消除缺口。
6. 说明可由用户补足500元或重新选择金额，余额及三个业务对象均无新增变动。

**可接受路径：**允许等义的业务表述和合法工具路径；不要求固定Agent数量、固定节点名或固定查询顺序。

**职责衔接：**资金；理财；整份计划预检

**落地前还需：**余额5000及完整适配产品；对三类写操作分别监测状态和回执；需把整单条件绑定到计划，而非只保存在自然语言摘要

## MA03｜停银行代扣、保留商户合同与卡片正常支付

**考察能力：**检验订阅、卡片和现金流解释之间的责任边界，避免用整卡限制替代精准业务。

**用户问题：**

> 只停掉视频会员的银行代扣，会员合同先保留，音乐照旧。再确认一下卡片正常支付会不会受影响。先展示详情，我确认后再办。

4. 用户明确确认后，视频银行授权变为STOPPED，商户合同仍ACTIVE，余额不变。

**可接受路径：**允许等义的业务表述和合法工具路径；不要求固定Agent数量、固定节点名或固定查询顺序。

**落地前还需：**分别记录商户合同、银行授权与卡片状态；执行器需独立断言合同与代扣，而非只断言一条取消回执

5. 另扣生活预留1000元和未来义务1200元，得到7000-1500-1000-1200=3300元上限。
